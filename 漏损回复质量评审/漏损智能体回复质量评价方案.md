# 漏损智能体回复质量评价方案（讨论稿）

日期：2026-10-24。

## 1. LLM 评审方法

建议使用大语言模型（LLM）逐项核对任务要求和回复依据，再形成整体结论。

评审需要回答以下问题：

- 用户要求回答什么？
- 回复是否回应了这些要求？
- 回复中的数值、事实和分析是否有依据？
- 建议和表达是否满足当前任务？

评审结果需要给出原文、依据和原因。不能只给总分，也不能凭篇幅或语言流畅度判断质量。

现有数值测评负责核实数值和口径。回复质量评审在此基础上，判断分析和建议是否成立。

本方案评价回复本身。原因是否实际查明、工单是否办结，需要结合业务结果另行判断。

## 2. 评审所需材料

评估 LLM 需要同时了解任务、回复和判断依据。

| 材料 | 内容 | 作用 |
|---|---|---|
| 用户问题与对话历史 | 本轮问题，以及需要继承的组织、时间和指标 | 确定当前任务 |
| 本题回复要求 | 必须回应的内容、条件适用项和可选项 | 判断是否遗漏 |
| 智能体原始回复 | 用户实际看到的内容 | 作为评审对象 |
| 数值基准与评价结果 | 已核实的数值、范围、期间和口径 | 衔接现有数值测评 |
| 业务数据与知识资料 | 分析使用的数据、有效业务规则和来源 | 检查事实、推理和建议 |
| 证据范围说明 | 哪些数据确实缺失，哪些材料未提供给评审 | 区分业务限制与评审资料不足 |

缺少可信依据时，LLM 仍可以评价表达和明确子问题的覆盖情况。对事实和原因，则需要保留无法判断。

参考回复可以帮助说明合格边界。不同措辞也可以满足要求，不能只按文字相似度评分。

## 3. LLM 按什么顺序评审

每条回复采用同一评审顺序。各阶段的判断分别保留，避免一个好印象影响全部评价。

### 3.1 确定本题要求

先根据问题、历史和业务规则，确定本题必须回应的内容。

例如，用户问“本月 A 小区漏损率为什么上升，先查什么？”。本题要求包括：

- 回应指定对象和期间的指标变化。
- 回应原因请求，并说明依据或判断限制。
- 给出具体核查动作和先后依据。

本题要求需要在评价回复前确定。LLM 可以辅助草拟，业务人员负责认可规则。不得按待评价回复已经写出的内容反推要求。

不同题型的要求不同：

| 任务类型 | 主要检查内容 |
|---|---|
| 数值查询 | 指定对象和期间的数值、单位及口径 |
| 状态判断 | 当前水平、比较标准和差距 |
| 趋势分析 | 可比期间、变化方向和幅度 |
| 重点对象筛选 | 对象范围、排序依据和优先顺序 |
| 原因分析 | 证据、可能解释和判断限制 |
| 处置建议 | 对象、动作、先后依据和验证方向 |
| 知识问答 | 适用条件、解释或步骤、有效来源 |

目标、同比、环比和排名不能成为全部题目的默认要求。

### 3.2 核对要求是否得到回应

LLM 将本题要求与回复逐项对应，判断以下情况：

| 判定 | 含义 |
|---|---|
| 已回应 | 有明确内容回应本项要求 |
| 回应不完整 | 提到了该项，但缺少要求中的内容 |
| 未回应 | 回复没有对应内容 |
| 无法判断 | 缺少判断是否回应所需的上下文 |

“有回应”只说明内容覆盖。回应是否正确，需要继续核对证据。

例如，“已经确认管道破裂”回应了原因请求。但如果缺少证据，这个原因判断仍可能不合格。

### 3.3 核对关键陈述是否有依据

LLM 需要找出回复中影响业务判断的陈述。

关键陈述包括：

- 数值和变化幅度。
- 超标、排名或重点对象判断。
- 趋势和贡献判断。
- 原因判断。
- 业务标准和处置依据。
- 已完成动作的声明。

每条关键陈述都需与可信材料对应。

| 证据关系 | 评审含义 |
|---|---|
| 有支持 | 数据或业务资料能够支持陈述 |
| 有矛盾 | 陈述与可信材料不符 |
| 缺少支持 | 已提供完整的判断材料，但材料不能支持陈述 |
| 无法核实 | 评审缺少核实所需的材料 |

“缺少支持”和“无法核实”需要分开。例如，智能体当时使用了工单，评审却未取得工单。此时不能直接认定智能体虚构工单。

对于数值陈述，复用现有测评基准。回复新增的派生数值和补充事实，也需要核对。

### 3.4 判断分析和建议是否成立

有正确数据，还需要检查推导过程。

LLM 需要判断以下问题：

- 比较对象和统计口径是否一致？
- 数据是否支持趋势和重点对象判断？
- 是否将变量关联直接解释为因果？
- 是否将待验证假设写成已确认原因？
- 建议是否针对当前对象和已知问题？
- 建议是否符合有效业务规则和用户权限？

数据不足时，回复可以说明无法确认原因。若用户还询问下一步，回复仍需给出有依据的核查方向。

这类回复可以合格，但业务原因尚未查明。若数据足够却回避回答，则需要检查是否遗漏要求。

### 3.5 汇总维度判断和整体结论

LLM 根据前面的核对结果，评价第 4 节的各维度。整体结论再按第 5 节的规则形成。

表达在事实和分析之后评价。语言清楚不能抵消关键事实错误。

## 4. 统一评价的 5 个维度

每个维度都需要使用明确的合格条件。

| 维度 | 判断对象 | 合格条件 | 常见不合格表现 |
|---|---|---|---|
| 问题覆盖 | 本题要求与回复的对应关系 | 全部必须项得到回应，保留正确的对话条件 | 只回答数值，遗漏原因或核查请求 |
| 证据一致 | 回复中的事实和确定性表述 | 关键事实有支持，数值与口径符合基准 | 编造数据、来源、阈值或执行结果 |
| 分析合理 | 数据到结论的推导 | 比较可比，推导成立，假设与确认事实分开 | 仅凭指标上升就确认爆管 |
| 建议可用 | 回复中的处置建议 | 对象和动作明确，先后依据合理，符合业务规则 | 只说“加强管理”，无法据此执行 |
| 表达清楚 | 内容组织和呈现 | 结论明确、单位清楚、表文一致 | 重点难找，或表格与文字互相矛盾 |

多轮条件纳入问题覆盖。数据时效和确定性表述纳入证据一致与分析合理。

建议可用只在任务需要建议时适用。单纯查值且没有分析内容时，分析合理也可以不适用。

回复中主动补充的内容仍需接受评审。额外编造原因，不能因用户没有询问原因而免于评价。

## 5. 怎样形成整体结论

建议先采用定性结论，不急于确定总分和权重。

LLM 需要区分以下问题：

| 问题类型 | 含义 |
|---|---|
| 关键错误 | 会误导核心业务判断的错误 |
| 内容不足 | 遗漏要求，或内容不足以支持当前任务 |
| 表达问题 | 内容呈现妨碍理解或使用 |
| 无法判断 | 评审材料不足以形成可靠结论 |
| 不适用 | 当前任务没有该项要求 |

关键错误包括以下情况：

- 关键数值、组织、期间或口径错误。
- 核心结论与证据相反。
- 编造影响决策的原因或业务标准。
- 将无数据解释为无异常。
- 虚构已经完成的动作。

整体结论按以下优先顺序形成：

| 优先顺序 | 结论 | 判定条件 |
|---|---|---|
| 1 | 不合格 | 已有证据证明存在关键错误 |
| 2 | 无法判断 | 尚未确认关键错误，但缺少判断核心要求所需的材料 |
| 3 | 待完善 | 有明确遗漏或不足，但未确认关键错误 |
| 4 | 合格 | 全部必须项已回应，适用维度均满足合格条件 |

不适用项不影响合格判断。已经证实的关键错误，不因另一项无法判断而被隐藏。

最终评审需要说明以下内容：

- 本题要求及逐项回应情况。
- 各维度的判断及原因。
- 问题对应的回复原文。
- 支持判断的数据或业务依据。
- 整体结论及需要人工核实的争议。

对于遗漏内容，没有可引用的原文。此时指出缺少哪项要求即可。

## 6. 用同一个问题说明评审结果

以下为假设场景，用于说明判断方法。

用户问题：“本月 A 小区漏损率为什么上升，先查什么？”

已知材料表明漏损率上升，但不足以确认物理原因。业务核查规则要求先核对计量和数据完整性。

待评回复：“已经确认地下管道破裂，建议加强管理。”

LLM 应形成以下判断：

| 维度 | 判断 | 原因 |
|---|---|---|
| 问题覆盖 | 待完善 | 回应了原因，但未说明变化，核查动作也不具体 |
| 证据一致 | 不合格 | 材料不能支持“已经确认地下管道破裂” |
| 分析合理 | 不合格 | 指标上升不能直接证明管道破裂 |
| 建议可用 | 待完善 | “加强管理”没有对象、动作和先后依据 |
| 表达清楚 | 合格 | 文字可以理解 |

整体结论为不合格。关键问题是原因判断超出证据支持范围。

如果回复说明暂时无法确认原因，并按业务规则提出核查方向，可以判回复合格。实际原因仍需核查。

这个例子说明评审需要保留逐项依据。仅判断“回答是否完整”或“表达是否清楚”，会漏掉核心问题。

## 7. 人工评审与用户反馈如何参与

LLM 负责按规则评审，业务人员负责认可标准和核实争议。

业务人员主要需要明确以下内容：

- 各类任务必须回答什么。
- 哪些证据足以支持业务判断。
- 哪些错误会误导决策。
- 数据不足时，哪些回应可以接受。
- 不同角色需要怎样的分析深度。

人工还需要检查评估 LLM 的判断是否可靠。重点检查关键错误漏检、合理回复误判和长回复偏好。

模型自报置信度不能替代人工核对。规则变化后，也需要确认相同要求下的判断是否稳定。

用户反馈用于发现评价标准遗漏的需求。反馈经核实后，再用于补充内容要求或修订业务判断依据。

用户满意度与回复正确性需要分别记录。用户反馈的填写维度和方式见第 8 节。

## 8. 用户反馈维度与填写方式

建议按以下 5 个维度设计反馈项。用户填写时，使用业务人员能理解的表述。

### 8.1 反馈维度

| 反馈维度 | 用户需要判断什么 | 可选的问题原因 |
|---|---|---|
| 需求满足 | 有没有回答想问的问题 | 理解错了问题、没有直接回答、遗漏关键内容 |
| 数据与事实 | 数值、对象、时间和口径是否正确 | 数值不对、对象或期间不对、口径不对、数据过旧 |
| 分析依据 | 分析和结论是否有依据 | 没说明依据、结论与数据不符、原因判断过于确定 |
| 建议可用 | 建议能否用于当前工作 | 建议太笼统、不符合实际、缺少具体动作 |
| 表达清楚 | 能否看懂并找到重点 | 太长或重复、术语难懂、重点不清、图表与文字不一致 |

这些维度用于收集使用感受和问题线索。用户反馈不能直接替代数值核对和业务评审。

### 8.2 填写方式

建议采用“总体评价、问题原因、补充说明”的结构。

| 填写内容 | 是否必填 | 选项或引导文字 |
|---|---|---|
| 总体评价 | 必填 | 有帮助；有帮助，但需要修改；没有解决问题；暂时无法判断 |
| 问题原因 | 按需多选 | 从上述 5 个维度中选择具体问题 |
| 补充说明 | 选填 | 具体哪里有问题？你希望补充或改成什么？ |

用户无需每次逐项评分。认为回复有问题时，再选择问题原因。

### 8.3 适用条件与反馈处理

反馈需要允许用户表达无法判断：

- 对数据正确性无法判断时，可以选择“无法判断”。
- 对分析依据无法判断时，可以选择“无法判断”。
- 查值回复没有处置建议时，无需评价“建议可用”。

系统应自动关联问题、回复和版本，减少用户填写内容。

用户反馈用于发现问题。数值或原因是否确实错误，仍需核实。核实结果再用于修订评价要求和补充测试题。
