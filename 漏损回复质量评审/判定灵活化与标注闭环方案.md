# 判定灵活化与标注闭环方案

| 项目 | 内容 |
|---|---|
| 文档日期 | 2026-11-06 |
| 状态 | 待评审，未实施 |
| 关联文档 | [答案比对与值抽取优化方案.md](答案比对与值抽取优化方案.md)、[过程评测优化方案.md](过程评测优化方案.md) |
| 一句话目标 | 让「合格/不合格」由七个维度的影响决定，而不是由一条覆盖率线决定；让每次人工平反沉淀成可回归的标注。 |

---

## 1. 一页看懂

要解决的是两个独立的问题，必须分开做：

| 问题 | 现状 | 做法 |
|---|---|---|
| **判定太僵硬** | 覆盖率必须 1.0 才合格；缺一行、漏一列都出局，不区分这行重不重要 | 给每个基准项定重要性，差异分三级（阻断/扣分/忽略），结论取最重一级 |
| **没有可用的真值** | 平反只存结论、不存原因；当前项目 `review_notes` 是 0 行 | 平反时补一张「纠错单」：结论 + 归因 + 维度 + 理由 + 证据，append-only |

顺序不能反：**先有标注，才能量化判定改动是变好还是变松**。所以分四期：

| 期 | 内容 | 工期 | 产出 |
|---|---|---|---|
| P0 | 标注闭环（平反 + 原因） | 1–1.5 天 | 详情页可填「为什么平反」，写进 `annotations.csv` |
| P1 | 离线回放器 | 1 天 | 从本项目 `runtime/` 复算结论，不跑智能体、不连库、不调 LLM |
| P2 | 判定 v2（按影响分级） | 2–3 天 | v1/v2 对照报告，默认关闭，可随时切回 |
| P3 | 校准与切换 | 0.5 天 | 人工金标达标后，新批次启用 v2 |

每期都能单独验收、单独回滚，不存在「改一半不能用」的中间态。

## 2. 先对齐三个词

### 2.1 平反（verdict override）

你现在做的：看完题，认为系统判错，点一个按钮改成「合格 / 部分作答 / 不合格 / 无法评估」。
作用：覆盖这一题的最终结论，指标随之刷新。
问题：只留下结论，没留下原因。同一句「我判它合格」，可能是抽取没抓到、可能是阈值太严、也可能是契约本身错——这三种要改的地方完全不同。

### 2.2 标注（annotation）

在平反的基础上多记三样东西：

- **错在哪一环**（归因）：抽取漏了 / 判定太严 / LLM 误判 / 契约错 / 范围理解错 / 其他
- **错在哪一维**：七维多选
- **凭什么**：一句理由 + 可选原文证据

一条标注 = 一个带标签的失败样本。它既能当「这题应该是什么结论」的金标，也能当「先修哪里」的统计依据。

### 2.3 金标（calibration set）

把标注存成一个固定位置的 CSV（`annotations/annotations.csv`），回放器每次重算都拿它对答案。它是「优化率」的分母。

| | 平反 | 标注 | 金标 |
|---|---|---|---|
| 存什么 | 最终结论 | 结论 + 归因 + 维度 + 理由 | 多条标注的集合 |
| 谁产生 | 评审人点按钮 | 评审人填一张小单 | 回放器按题取最新一条 |
| 用来做什么 | 改这一题的结论和指标 | 定位系统错在哪 | 算优化率、做回归 |

## 4. P0：标注闭环

### 4.1 用户在页面上会经历什么

以 LS-008 为例（自动判「部分作答」，你认为该判「合格」）：

1. 打开详情页，顶部还是四个平反按钮。
2. 点「合格」——**结论立即保存**，和今天完全一样，不打断。
3. 因为与自动结论不同，按钮下方出现一条浅色提示条：
   `本次平反与自动结论（部分作答）不同，补充原因？ [展开] [跳过]`
4. 展开后是一张小表单：
   - 归因（单选，必选）：抽取漏了 / 判定太严 / LLM 误判 / 契约或基准错 / 范围理解错 / 其他
   - 维度（多选，默认勾选自动结论里判为 MISMATCH 的维度）
   - 理由（一句话，选填）
   - 证据（选填，可粘贴答案原文）
5. 保存 → 追加一条标注；跳过 → 该题标记「未说明原因」，之后随时可补。
6. 详情页底部出现「平反历史」：时间 / 人 / 结论从什么改到什么 / 归因 / 理由。

**关键约束**：平反行为不变，原因选填。不填不影响结论和指标，只是不进归因统计。

### 4.2 数据结构

不动 SQLite 表结构：`review_notes` 继续存「当前结论」（指标读它），新标注另存一份 append-only CSV。

存储位置：`annotations/annotations.csv`（项目根目录，随项目走，可直接用 Excel 打开、筛选、排序）。

列定义（一行 = 一次平反动作）：

| 列 | 说明 |
|---|---|
| `run_id` | 批次号 |
| `case_id` | 题号 |
| `auto_verdict` | 平反前的自动结论 |
| `manual_verdict` | 平反后的结论 |
| `reason_code` | 归因枚举，见 4.3 |
| `dimensions` | 七维，多个用 `;` 分隔，如 `row_coverage;numeric_accuracy` |
| `note` | 一句话理由 |
| `evidence` | 可选的原文片段 |
| `annotator` | 操作人（默认取系统用户名） |
| `prompt_version` / `model` | 自动结论当时的评估版本与模型 |
| `code_version` | `git rev-parse --short HEAD` |
| `created_at` | ISO 时间 |

文件样子（UTF-8 带 BOM，Excel 直接打开不乱码）：

```csv
run_id,case_id,auto_verdict,manual_verdict,reason_code,dimensions,note,evidence,annotator,prompt_version,model,code_version,created_at
20261106_100421_2e18,LS-008,PARTIAL,QUALIFIED,THRESHOLD_STRICT,row_coverage,"缺的 23 个值是题目没点名的单位，已给出的数值全部正确","",xiaoxin,v1,deepseek-v4-flash,962af0a,2026-11-06T11:30:00+08:00
```

为什么用 CSV 而不是新表：

- 不给本地 SQLite 加表，schema 不变，升级不用做迁移；
- 人工可以直接在 Excel 里补理由、改归因；
- append-only，天然留痕，git 里也能 diff；
- 回放器按 `(run_id, case_id)` 取最新一行即可，不需要查询引擎。

写入方式：模块级锁 + 追加写（服务单进程运行足够）；文件不存在时先写表头。

为什么不用现有的 `review_notes.note` 一列了事：平反会反复改（今天合格、明天改判部分），upsert 会覆盖历史；而「当时为什么这么判」本身就是资产，必须 append-only。

### 4.3 归因枚举

| code | 含义 | 典型信号 | 后续动作 |
|---|---|---|---|
| `EXTRACT_MISS` | 抽取没抓到 | 回答里有该值，`reconcile` 记成 ABSENT | 补抽取规则，加回归用例 |
| `THRESHOLD_STRICT` | 判定太严 | 数值全对但覆盖率不到 1.0 | 调重要性/阈值（本期重点） |
| `LLM_MISJUDGE` | LLM 判错 | 语义维度误报 | 改 prompt，加强证据约束 |
| `CONTRACT_WRONG` | 契约或基准错 | SQL 值/口径本身不对 | 修 `contracts.json` / 黄金集 |
| `SCOPE_MISS` | 范围理解错 | 多给或少给被当错 | 补 `coverage_policy` |
| `OTHER` | 其他 | — | 人工说明 |

### 4.4 接口

```text
POST /api/runs/{run_id}/cases/{case_id}/verdict
  body: { verdict, note?, reason_code?, dimensions?, evidence? }
  行为：verdict 为空 = 撤销平反（老行为，只更新 review_notes）；带 reason_code = 同时追加一行 CSV
GET  /api/runs/{run_id}/cases/{case_id}/annotations   → 读 CSV，返回该题平反历史
GET  /api/annotations/summary?run_id=                  → 按 reason_code 聚合计数
```

向后兼容：不带 `reason_code` 时只更新 `review_notes`，与今天一致；旧批次不需要迁移。

### 4.5 金标快照

`annotations/annotations.csv` 本身就是金标来源，回放器直接读它，按 `(run_id, case_id)` 取最新一行。需要给某一版定格时再复制一份快照：

```bash
python -m evaluator.annotations snapshot --out annotations/calibration_20261106.csv
```

快照与主文件同格式，只是去重后一行一题，方便对比不同时间的金标差异。

### 4.6 版本戳

`code_version` 取 `git rev-parse --short HEAD`，`prompt_version` 取存档里 LLM 评估的版本。规则一改，旧标注的**归因**可能失效（那时确实是抽取问题，现在不是了），但**结论**这个锚点始终有效。两者分开存，才能在规则升级后仍然复用历史标注。

### 4.7 验收

- 平反一题并填原因 → `annotations/annotations.csv` 多一行，Excel 打开不乱码。
- 不填原因 → 结论照常生效，不写 CSV。
- 反复平反同一题 → CSV 多行，`review_notes` 只留最新结论。
- `snapshot` 命令能生成去重后的快照，条数 = 去重后的题数。

## 5. P2：判定灵活化

### 5.1 原则：重要性由契约定，不由 LLM 现场发挥

如果把「这行重不重要」交给 LLM 每题现判，结论会重新变得不可复现、不可回归——这正是现在「结论抖动」的来源。

所以分工是：

- **重要性**：来自契约（题目要求哪些行/字段）+ 明确的配置规则（如零值行是否豁免）。可审计、可回归。
- **语义判定**：LLM 判断期间/范围/粒度/口径，但必须给出可在回答原文中定位的证据，否则不构成阻断。
- **数值对错**：程序按容差算，永远是阻断项。

### 5.2 七维判定矩阵

| 维度 | 判据 | 判定方 | 不满足时的影响 |
|---|---|---|---|
| 数值准确 | 逐值比契约容差，容差按答案末位放宽 | 程序 | 有确认错值 → **阻断** |
| 行覆盖 | 只对「题目要求的行」计分：`top_n` 只看前 N 行；`all_rows` 看全部；缺失先回原文补抽 | 程序 + 契约 | 关键行缺 → 阻断；普通行缺 → 扣分；范围外 → 忽略 |
| 字段覆盖 | `required` 指标是否给全 | 程序 + 契约 | 缺 required → 阻断；缺 optional → 忽略 |
| 期间 | 回答声明的年月 vs SQL 绑定参数 | LLM + 原文证据 | 不一致 → 阻断 |
| 范围 | 组织集合与筛选条件 | LLM + 原文证据 | 缺主体 → 阻断；多给 → 忽略 |
| 粒度 | 明细 vs 汇总、单月 vs 累计 | LLM + 原文证据 | 不一致 → 阻断 |
| 单位口径 | 万/亿/%/pp 换算与统计口径 | 程序换算优先 | 换算后仍不一致 → 阻断 |

### 5.3 差异分三级

| 级别 | 含义 | 例子 |
|---|---|---|
| `BLOCKING` | 结论性错误，数字或口径是错的 | 数值超容差；期间不一致；题目点名的单位缺失 |
| `DEGRADING` | 部分信息缺失，但不改变主结论 | 范围内普通行缺一行；required 字段缺一个 |
| `COSMETIC` | 表达差异或补充信息 | 多给单位；汇总行；契约声明可选的零值行 |

### 5.4 结论合成

```text
若 抽取覆盖率 < 0.5           → UNEVALUABLE（不是答错，是没抽到）
否则若 存在 BLOCKING          → UNQUALIFIED
否则若 存在 DEGRADING         → PARTIAL
否则                          → QUALIFIED
```

替代现在的：

```text
coverage >= 1.0 且 value_recall >= 1.0 → QUALIFIED    ← 这一条要删掉
```

### 5.5 6 行对 7 行走查

| 情形 | 判定 | 结论 |
|---|---|---|
| 缺的那行在题目范围内、非零、required | 1 条 `DEGRADING` | `PARTIAL`（不是不合格） |
| 缺的那行值为 0，且配置 `zero_value_rows = optional` | `COSMETIC` | `QUALIFIED`，记一条提示 |
| 题目是「前 3 名」，SQL 返 7 行 | 后 4 行本就不要求 | `QUALIFIED` |
| 回答正文里其实写了，抽取没抓到 | 先补抽；补不到 | `UNEVALUABLE`，不算答错 |

### 5.6 指标口径

保留现有 `accuracy = QUALIFIED / 可评估题数`，另加一个加权完成度：

```text
weighted_completion = (QUALIFIED + 0.5 × PARTIAL) / 可评估题数
```

两个数并排展示。这样「部分作答」不再被默默当成 0 分，同时历史口径不变、可对比。

### 5.7 `coverage_policy` 落地

这个字段已经在契约里，但从未被判定读取。P2 要接上：

| mode | 语义 | 用在哪类题 |
|---|---|---|
| `all_rows` | 基准每行都要求 | 「各单位 / 全部」类 |
| `top_n` + `n` | 只要求前 N 行 | 「最高/最低前三家」类 |
| `all_fields` | 只看字段是否给全 | 标量题（单月产销差率等） |
| `minimum` | 允许的覆盖率下限 | 全局兜底，默认 1.0，个别题可放宽 |

141 道题目前全是默认值，需要由 `golden_builder` 按题型回填，或在 `contracts.json` 上人工确认一遍（72 道明细题优先）。

### 5.8 程序判不了的那一半

`reconcile` 返回 `available=False` 时，结论完全由 LLM 给出，没有程序兜底（当前批次占一半）。这类题要补两条约束：

1. **缺失类判定必须可核验**：LLM 说「31 行全缺」，程序要回原文核对行键（组织名）是否真的没出现、或出现但无数值；核不上的降为 `DEGRADING` 并转人工复核。
2. **不得因抽取失败判不合格**：`available=False`、且 LLM 只能给出「无法定位」时，结论是 `UNEVALUABLE`，不是 `UNQUALIFIED`。

这两条并入 P2，不额外加期。

## 6. P1：离线回放器与验收

### 6.1 `recompare` 做什么

不调用智能体、不连数据库、不调 LLM，只从本项目 `runtime/` 的批次存档复算：

```text
contracts_snapshot.json + agent_answer.json + sql_snapshot.json
        │
        ├─ reconcile()        → 逐值三态（HIT / MISS / ABSENT）+ 覆盖率
        ├─ verdict_policy     → v1 或 v2 结论
        └─ annotations.csv    → 与人工结论对比
```

命令：

```bash
python -m evaluator.recompare --runtime runtime --policy v1 --out out/recompare/v1
python -m evaluator.recompare --runtime runtime --policy v2 --annotations annotations/annotations.csv --out out/recompare/v2
```

### 6.2 输出

- `report.md`：人看的结论
- `report.json`：逐题明细（旧结论、新结论、覆盖率、归因、是否变化）
- `cases.csv`：可直接拖进 Excel 复核
- 控制台摘要：迁移矩阵 + 与金标的一致率

### 6.3 「优化率」怎么定义

**有金标时（正式口径）**

| 指标 | 定义 | 目标 |
|---|---|---|
| 假阴性率 | 人工判合格、系统判部分/不合格 的题数 ÷ 人工判合格的题数 | < 5% |
| 假阳性率 | 人工判不合格、系统判合格 的题数 ÷ 人工判不合格的题数 | 不高于 v1 |
| 真错值放过 | 存在确认错值却判合格的题数 | 0 |

**没有金标时（只能看方向）**

- 结论迁移率：多少题结论变了、往哪个方向变
- 不合格但无错值的题数
- PARTIAL 中数值全对的题数
- 抽取失败被当答错的题数

这组数字能证明「变松了」，不能证明「改对了」——所以它不能当上线依据。

### 6.4 门槛

| 门槛 | 条件 | 不满足怎么办 |
|---|---|---|
| G1 复现 | v1 在本项目已有批次上复现存档结论（当前 5/5；样本累计到 20 题后要求 ≥ 95%） | 先修回放器，不许往下走 |
| G2 金标 | 人工集 ≥ 20 题，假阴性 < 5%、假阳性不升 | 补标注或调规则 |
| G3 安全 | 真错值判合格 = 0 | 直接否决 |
| G4 可解释 | 每条非合格结论至少有 1 条带证据的 finding | 改输出结构 |

### 6.5 一句提醒

基线批次与线上同版本，不存在版本差；但规则每改一次，都要用同一批样本重放，才能保证可比。旧批次不重算、不覆盖；v2 只对新批次生效。

## 8. 需要你拍板的五件事

1. **范围内缺一个非零行**：判 `PARTIAL` 可以接受吗？（建议可以）
2. **零值行是否默认豁免**：建议不默认豁免——「哪些单位漏损为 0」本身就是答案，豁免会放过真错；需要豁免的题由契约声明。
3. **准确率口径**：保留「只数 QUALIFIED」，另加加权完成度，还是直接把 PARTIAL 记 0.5 分？（建议前者）
4. **归因六类够不够**：`EXTRACT_MISS / THRESHOLD_STRICT / LLM_MISJUDGE / CONTRACT_WRONG / SCOPE_MISS / OTHER`。
5. **平反原因是否必填**：建议选填，不填标黄，不阻断操作。

## 9. 风险与不做的事

| 风险 | 对策 |
|---|---|
| 标注太少，统计不可信 | 先攒到 20 条再谈优化率；不足时只用结构指标看方向 |
| 判定放松后放过真错值 | 错值永远是 BLOCKING，不受重要性规则影响 |
| 重要性靠人拍脑袋，规则难维护 | 重要性写进契约，回放器可逐题追溯依据 |
| 程序判不了的题仍靠 LLM | 缺失类判定必须回原文核验（§5.8），核不上转人工 |
| 标注归属不清 | 记录 annotator + 时间 + 版本戳 |

不做的事：

- 不改 SQL 基准的生成方式，不改智能体调用。
- 不自动覆盖历史批次的结论。
- 不让 LLM 直接决定重要性或最终结论。
- 不在本期处理多轮对话的答案继承。

## 附录 B：finding 结构（P2）

```json
{
  "dimension": "row_coverage",
  "code": "MISSING_ROW",
  "impact": "DEGRADING",
  "coordinate": {"key": "光明水务公司|202606"},
```

结论不是「覆盖率多少」，而是「有哪些 finding、每条多严重」——这是从「一个数」到「一张清单」的转变，也是灵活性的落点。
